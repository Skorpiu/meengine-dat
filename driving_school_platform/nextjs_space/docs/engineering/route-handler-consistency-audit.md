# Route Handler Consistency Audit

## Scope

This document maps **current patterns** in `app/api/**/route.ts` handlers for the DAT Next.js app. It is a **read-only audit** to guide small, focused refactor batches—not a runtime change and not a promise to refactor everything at once.

It complements the broader [engineering-excellence-audit.md](./engineering-excellence-audit.md) (architecture, data access, CI, demo policy) by going **route-by-route** on auth, guards, validation, and response contracts.

**Out of scope for this audit:** Prisma schema changes, billing provider integration, demo sandbox behavior changes, signup hardening, i18n, and platform product expansion.

---

## Desired route handler baseline

When adding or refactoring handlers, aim for:

| Concern                        | Baseline                                                                                                                                                                                                       |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Auth / roles**               | Single entry (`verifyAuth` or a thin wrapper) with explicit allowed roles; no ad-hoc string checks scattered in the handler body.                                                                              |
| **Tenant / platform boundary** | Tenant routes: `guardTenantAuthenticatedRoute` after session org is known. Platform routes: `decidePlatformSurfaceAccess` + host rules. Public routes: document why host resolution alone is enough.           |
| **Demo**                       | Mutations on tenant admin surfaces: `decideDemoRouteMutation` (or specialized sandbox helpers for limited creates). Reads: no hidden writes; demo policy documented.                                           |
| **Validation**                 | Zod (or shared schemas in `lib/validation`, `lib/config-validation`) **before** Prisma writes; sanitize where `validateRequest` already does.                                                                  |
| **Response contract**          | Prefer `successResponse` / `errorResponse` (or documented platform DTOs in `lib/platform/contracts`) so clients see predictable shapes. Stable `code` fields for policy errors (demo, calendar range, signup). |
| **Errors**                     | `withErrorHandling` for consistent logging and 500 sanitization; no raw provider/stack details to clients.                                                                                                     |
| **GET safety**                 | GET handlers are read-only (no `deleteMany` / side-effect maintenance). Bounded query params where lists can grow (calendar max range, pagination when needed).                                                |
| **Size**                       | Thin HTTP layer; orchestration in `lib/*` services when a route exceeds ~150 lines or mixes many modes.                                                                                                        |

## Findings

| ID      | Priority | Area              | Finding                                                                                                                                                                                                                          | Evidence                                                                                                                          | Recommended next step                                                                                             |
| ------- | -------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| RHC-001 | P1       | Response contract | **Two dominant success shapes:** `{ success: true, data }` (`api-utils`) vs flat resource keys (`{ lessons }`, `{ vehicles }`, `{ users }`).                                                                                     | `app/api/admin/lessons/route.ts` (calendar branch), `admin/vehicles/route.ts`, `admin/users/route.ts` vs `admin/cleanup/route.ts` | **route-response-contract-baseline** batch: document canonical shapes; migrate high-traffic routes incrementally. |
| RHC-002 | P1       | Auth              | **Split auth entrypoints:** `verifyAuth` + `withErrorHandling` vs raw `getServerSession` + inline role checks.                                                                                                                   | Compare `admin/lessons/route.ts` vs `admin/settings/route.ts`, `admin/vehicles/route.ts`                                          | Align admin surfaces on `verifyAuth` (or shared `requireTenantAdmin`) without changing authorization rules.       |
| RHC-003 | P1       | Tenant guard      | **Addressed:** vehicle routes call **`assertVehicleTenantHost`** after feature access (`lib/vehicles/vehicle-route-access.ts`).                                                                                                  | `app/api/admin/vehicles/route.ts`, `vehicles/update-status`, `vehicles/update-maintenance`                                        | —                                                                                                                 |
| RHC-004 | P1       | Demo guard        | **Addressed:** status/maintenance use **`rejectDemoVehicleManagementMutation`**; admin PUT/DELETE unchanged (already demo-guarded).                                                                                              | `lib/vehicles/vehicle-route-access.ts`, vehicle API routes                                                                        | —                                                                                                                 |
| RHC-005 | P1       | Security          | **Partially addressed:** HTTP error bodies sanitized via `lib/billing/webhook-http.ts` (stable `code`, no `detail` / raw provider messages). **Still open:** `withErrorHandling`, provider signature verification, IP allowlist. | `app/api/billing/webhooks/[provider]/route.ts`, `lib/billing/webhook-http.ts`                                                     | PSP hardening batch when a real provider is in scope.                                                             |
| RHC-006 | P2       | Handler size      | **Addressed:** admin lessons collection + `[id]` mutations extracted to `lib/lessons/*` (queries, mappers, create, update/delete services).                                                                                      | `app/api/admin/lessons/**`, `lib/lessons/*`                                                                                       | Optional: shared GET-by-id query helper (low priority).                                                           |
| RHC-007 | P2       | Validation        | **Signup** uses manual JSON parsing; no Zod/`validateRequest`.                                                                                                                                                                   | `app/api/signup/route.ts`                                                                                                         | Optional schema alignment batch (behavior already constrained by demo/tenant rules).                              |
| RHC-008 | P2       | Calendar reads    | **Addressed:** admin, instructor, and student calendar GETs use `validateLessonCalendarRange` (max 90 days, stable error codes).                                                                                                 | `lib/lessons/calendar-range.ts`, `app/api/*/lessons/route.ts`                                                                     | —                                                                                                                 |
| RHC-009 | P2       | Error handling    | Many **getServerSession** routes use per-handler `try/catch` + `console.error` instead of `withErrorHandling`.                                                                                                                   | `admin/settings`, `admin/feature-flags`, `admin/vehicles`, etc.                                                                   | Wrap exports or use shared inner handler to centralize 500 responses.                                             |
| RHC-010 | P2       | Demo errors       | Demo denials mix **`NextResponse.json({ error, code })`** with **`errorResponse`** (no `code` field).                                                                                                                            | `admin/lessons` POST vs `admin/cleanup` demo branch                                                                               | Standardize stable `code` on policy errors across routes.                                                         |
| RHC-011 | P2       | Platform          | **Platform organizations** correctly uses `decidePlatformSurfaceAccess` but response/error style differs from tenant admin.                                                                                                      | `app/api/platform/organizations/route.ts`                                                                                         | Document as intentional; add audit logging in platform batch.                                                     |
| RHC-012 | P3       | Public reads      | **Categories / transmission-types** are unauthenticated global lists.                                                                                                                                                            | `app/api/categories/route.ts`, `transmission-types/route.ts`                                                                      | Confirm acceptable for production; add cache headers if needed.                                                   |
| RHC-013 | P3       | DTO / includes    | **Partially addressed:** `LESSON_LIST_INCLUDE` in `lesson-queries.ts`; GET bodies via `lesson-mappers.ts` (pass-through today, no field stripping). **Still open:** trim nested `user` fields when UI catalogued.                | `lib/lessons/lesson-queries.ts`, `lib/lessons/lesson-mappers.ts`                                                                  | Optional batch 6 minimization.                                                                                    |
| RHC-014 | P3       | Config admin      | Settings, feature-flags, config-history share patterns but duplicate boilerplate.                                                                                                                                                | `admin/settings`, `admin/feature-flags`, `admin/config-history`                                                                   | Extract thin `lib/admin/config-routes` helpers when touching config next.                                         |

**Note:** No **P0** items are listed. Remaining risks are **consistency and maintainability**, except billing webhook security which is already tracked as **P1** in the engineering excellence audit (**EEA-006**).
